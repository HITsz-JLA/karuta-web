# 在线歌牌对战

## 目标

在线模式复用 `karuta-web` 已有的服务器本地 ZIP 数据包和浏览器 IndexedDB 资源。两名玩家进入同一房间后，双方看到同一组 HITsz-JLA 卡面，听到服务器从本地数据包读取的歌曲片段，并抢先点击对应卡面得分。

这是对 [shinycolors-song-guess](https://github.com/Sallyn0225/shinycolors-song-guess) 的前后端分层和房间交互模式的参考，不引入其素材、曲库或 UI。

## 使用流程

1. 管理员在 `/admin` 上传精简包或完整包。
2. 两名玩家在首页加载同一个服务器数据包。加入房间时，如果浏览器还没有该包，在线页面会自动下载并导入本地 IndexedDB。
3. 房主进入「在线 1v1」，选择有歌曲的数据集和 2–24 张卡牌，创建房间并分享 6 位房间码。
4. 对手输入房间码加入；双方确认卡面已同步后点击准备。
5. 每回合服务器随机选择一张剩余卡牌的一首歌曲，浏览器同时播放音频；玩家点击卡面抢牌，服务器按先到达的正确点击结算。

## 协议边界

客户端通过同源 `/ws` 发送 `createRoom`、`joinRoom`、`ready` 和 `claim`，服务器广播房间、回合开始、抢牌反馈、回合结算和对局结束消息。

房间服务只在内存保存房间和对局状态，不保存昵称历史或对局内容。服务器不会在 `room`、`roundStart` 消息中下发歌曲名称或答案卡牌；每回合只发一次性音频 URL，凭证在当前回合结束后失效。`roundResult` 才公开对应歌曲和卡面。

卡牌在协议中使用由 `牌号 + 原始图片路径/文件名 + 作品名` 生成的稳定键。IndexedDB 仍使用本地随机 blob 键，稳定键让两台设备导入同一包后可以找到同一张真实卡面。

## 部署前提

- Node.js 运行 `npm ci` 后使用 `npm run build` 和 `npm start`。
- 反向代理必须同时转发 `/api` 和 `/ws`，并保持 WebSocket Upgrade；同源 HTTPS 页面使用 `wss`。
- `data-packages/` 中必须保留在线房间引用的数据包；不要把 ZIP、管理员密码、`.env` 或令牌提交到 Git。
- 当前实现的房间状态是单进程内存状态，重启会结束正在进行的房间；需要多实例或持久化房间时，应先引入共享状态存储并重新设计一致性边界。

## 验证边界

`npm test` 覆盖房间创建/加入/准备/回合抢牌、无效房间 fail-closed 和 ZIP 单资源读取；`npm run build` 验证前端构建。以上属于代码/受控本地证据，不替代校园网双设备、人类验收、生产反向代理或 HTTPS 验证。
